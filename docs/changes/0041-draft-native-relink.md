# 正式发行先准备草稿，再校验原生材料

状态：1.4.0 发布流程变更。影响范围：GitHub Release、原生材料清单及维护者和安装者的说明。不替换打包的 `libplayer.so`，不改应用版本。

## 为什么暂停打标签

首次正常通过全部 [main CI](https://github.com/zerobiubiu/ZeroPlayer/actions/runs/44352891786) 的候选是 `f9b9a0f4c811c700428584e5bd75222617b493d9`；其远端归档的 32 份 JUnit XML 共 187/187 通过，含播放器队列 13/13。但原标签流程只附 APK 和摘要，即会公开。按照项目[第三方分发声明](../../THIRD_PARTY_NOTICES.md)，静态链接的原生播放栈还需要对应源码、实际配置、JNI 对象、静态库与接收者自行替换和重链接的步骤。CI 绿不等于这些材料齐备，因而没有用该提交打版本标签，也未将两项不完整附件公开。

## 两个发布动作

1. 推送已核对的 `vX.Y.Z` 标签，只运行签名作业，拒绝覆盖同标签草稿或已公开版本；将已验签的 APK 和摘要上传到**草稿**。
2. 在同一草稿补入已验证的 `ZeroPlayer-<版本>-native-relink-arm64-v8a.tar.xz` 与 `.sha256` 以及中文发行要点。在**同一标签**上手动运行 Release，触发独立公开作业。它没有 Android 签名配置，不执行归档内的代码：从 GitHub 重新下载四项，验上传状态、尺寸、GitHub 摘要、两个附件摘要、材料/库的固定身份和 APK 签名及包信息。公开前再次比对草稿正文、附件清单和远端标签；缺失、被替换或不符即停止并保留草稿。

普通用户只需 APK；开发者的源码与重链接材料与它同版提供。GitHub 自动生成的项目源码 ZIP 不含整套链接输入。历史版本材料的交付状态不据此追溯更改。

## 1.4.0 材料与验证

- 原版构建的 14 份源码压缩包逐份核对固定 SHA-256；保留其实际使用的配方、JNI 源、6 个 JNI 对象和 15 个静态归档。静态归档共 2,512 个实存成员，不是指回工作区的 thin archive。另含源码和 NDK 许可、工具版本与内部 `SHA256SUMS`；不含完整 NDK 或预制 `.so`。
- 材料包根目录有 `README.txt`、`relink.sh`、`objects/`、`lib/`、`downloads/`、`tools/mpv-static/` 和 `licenses/`。全新解包得到 106 个普通文件、63 个目录，无链接或特殊文件；清单核对 105 项。Linux x86_64 环境仅挂入所需对象、静态库、脚本及只读 NDK r29，在独立路径运行 `ANDROID_NDK_HOME=/ndk bash relink.sh /out`，不使用原工作区。开发者替换静态归档后可运行相同步骤；修改版不应预期保持官方哈希。
- 未剥离输出 111,890,120 字节，SHA-256 `f715de5a536b9c9b7af923b42d7c26a9e84cd48900fb723eb0e8b2f21e642a0f`；剥离后 26,908,632 字节，与原构建、仓库和本机正式 APK 中的 `libplayer.so` 逐字节相同。最终材料包 105,697,868 字节，完整包与库的 SHA-256 见[固定身份记录](../../tools/mpv-static/relink-materials.json)。
- 将本机正式 APK、实际材料包和两份摘要配合本机生成的草稿元数据运行[发行门禁](../../tools/verify-release-materials.py)，四项正例通过。缺材料、多附件、服务器长度或摘要错误、另一个内部自洽的材料包、等长但内容错误的 APK 原生库均被拒绝。正式 Release、预期外的标签及分支不会被当作可公开的该版本草稿。该离线检查不冒充 GitHub 附件下载，最终对外结果以实际工作流及发行页为准。
